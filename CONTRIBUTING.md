# Руководство по участию в разработке (`CONTRIBUTING.md`)

Данный документ описывает правила разработки, добавления новых автотестов, проверки качества кода и оформления коммитов в проекте **Product Catalog API Tests**.

---

## 1. Требования к окружению

- **JDK 21** (проверяется через `java -version`).
- **Gradle Wrapper** (`./gradlew` / `.\gradlew.bat`) — используется встроенная версия Gradle из репозитория.
- **IntelliJ IDEA** (Community или Ultimate) с поддержкой Kotlin.

---

## 2. Архитектурные правила

Проект следует принципу чёткого разделения ответственности:

1. **Никаких захардкоженных адресов и секретов**:
   - Адреса стендов (`BASE_URL`), спецификации (`SWAGGER_URL`), токены (`API_TOKEN`) и пароли никогда не сохраняются в коде, `properties`-файлах или тестах.
   - Для локального запуска используйте файл `.env` (он добавлен в `.gitignore`) или системные свойства `-DBASE_URL=... -DSWAGGER_URL=...`.
2. **HTTP-клиент (`clients/ProductsApiClient.kt`)**:
   - Отвечает только за формирование и отправку HTTP-запросов через REST Assured.
   - Не содержит тестовых проверок (`assertThat`), чтобы один и тот же метод клиента можно было использовать как в позитивных (`200 OK`), так и в негативных (`400`/`404`/`405`) сценариях.
3. **Модели данных (`models/`)**:
   - Отражают только реально существующие в контракте OpenAPI поля (`Product`, `Measure`, `ProductStatus`).
   - Аннотированы `@JsonIgnoreProperties(ignoreUnknown = false)` для раннего обнаружения недокументированных изменений контракта.
4. **Проверки (`assertions/ProductAssertions.kt`)**:
   - Переиспользуемые контрактные и бизнес-проверки выносятся в `ProductAssertions`.
   - Групповые проверки полей выполняются через `SoftAssertions`, чтобы при падении видеть сразу все несовпадения по карточке товара.
5. **Структура тестов (`tests/api/`)**:
   - Для каждого эндпоинта создаётся пакет с двумя классами: `*SmokeTest.kt` (`@ApiSmoke`) и `*RegressionTest.kt` (`@ApiRegression`).
   - Внутри `*RegressionTest.kt` сценарии группируются через `@Nested`-классы (`Позитивные и бизнес-проверки`, `Контрактные проверки`, `Граничные значения`, `Негативные проверки`).
   - Все тестовые классы и методы снабжаются понятными русскоязычными `@DisplayName`, `@Description` и шагами `reportStep("...")`.

---

## 3. Как добавить новый тест-кейс

1. Определите целевой эндпоинт и выберите соответствующий класс (`*SmokeTest.kt` для критичных P0 read-only проверок или нужный `@Nested`-блок в `*RegressionTest.kt`).
2. Если сценарий проверяет новый набор входных параметров уже существующего теста — добавьте новую строку `Arguments.of(...)` в провайдер данных в `ProductTestData.kt`.
3. Если сценарий новый:
   - Присвойте следующий номер `TC-XX` в `@DisplayName("TC-XX: ...")`.
   - Оберните вызов `apiClient` и блоки проверок в `reportStep("...")`.
   - Если тест изменяет состояние сервера (`DELETE`, `POST`, `PUT`), обязательно добавьте `@Tag("destructive")` и вызов `requireDestructiveOperationsAllowed()`.
4. Добавьте описание нового тест-кейса в [`docs/test-cases.md`](docs/test-cases.md).

## 4. Обязательные проверки перед созданием Pull Request

Перед отправкой изменений убедитесь, что проходят все проверки:

```bash
# 1. Статический анализ кода (Detekt) и автономные тесты конфигурации (без внешнего стенда)
./gradlew clean check

# 2. Полный прогон всех smoke и regression тестов на локальном контрактном стабе + генерация отчёта Allure 3
./gradlew --continue clean smokeTest regressionTest allureReport -DUSE_LOCAL_MOCK=true
```

Также проверьте, что в `git status` и `git diff` нет:
- реальных внутренних URL или IP-адресов;
- токенов, паролей или учётных данных;
- локальных абсолютных путей к домашней директории разработчика.

## 5. Правила именования веток и коммитов

### Ветки
- `main` — стабильная основная ветка.
- `feature/<short-name>` — добавление новых тестов или функциональности фреймворка (например, `feature/product-catalog-api-tests`).
- `fix/<short-name>` — исправление ошибок в тестах или конфигурации.
- `ci/<short-name>` — настройка пайплайнов CI/CD.
- `docs/<short-name>` — обновление документации.
- `refactor/<short-name>` — рефакторинг структуры без изменения тестового покрытия.

### Сообщения коммитов (Conventional Commits)
Используйте понятные сообщения в формате `<type>: <summary>`:
- `test: add boundary length cases for product lookup`
- `feat: support API key header authentication`
- `fix: handle trailing slash in download link endpoint`
- `ci: add static analysis and offline test steps`
- `docs: update test execution guide`
